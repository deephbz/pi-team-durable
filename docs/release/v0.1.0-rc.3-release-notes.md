# Pi Team Durable 0.1.0-rc.3: interrupt fixes and Worker Alert parity

Interrupt Alerts now behave as in Pi Team Bright, and role tools act only on
the parameters that Pi registers. This is a prerelease on npm `next`.

## Changes

- An interrupt Alert stops the run that is current when the Alert is
  delivered. 0.1.0-rc.2 chose the run when it accepted the Alert. The delivery
  records the run and an absolute 10-second settlement deadline before it
  aborts. A restart keeps both. It never aborts a newer run and never sends a
  second abort. An idle recipient gets a plain steer.
- If the run does not settle within 10 seconds, the Alert is admitted once with
  an unproved interruption outcome.
- A confirmed interruption adds `interruptedRun` to the obligation and to the
  `team.notice` entry data.
- Only the lead can interrupt. A role tool ignores every argument its schema
  does not declare, including a Worker's `interrupt`. Receipts stored by
  earlier versions still replay.
- A Worker `alert_send` with empty `text` or empty `task_id` now fails parameter
  validation, as in Pi Team Bright. 0.1.0-rc.2 returned `refused` with
  `invalid_fanout`. Whitespace-only text is still refused with `invalid_fanout`.

## Before deploy

The first open upgrades stored `ptb.deliver` tasks to task version 2. Their
inputs and checkpoints do not change. The upgrade is one-way: 0.1.0-rc.2 and
older nodes then park those deliveries as `task_too_old` and never admit them.
Back up the store, and stop every older node process first. Rollback means
restoring that backup.

A store still on 0.1.0-rc.1 also gets the 0.1.0-rc.2 indexed-format migration,
which is one-way too.

## Known issues

1. An Alert is lost when the recipient's model errors. It shows as
   unanswered. Pi Team Bright retries it; this package does not.
2. `team_sync` can replay pages that an earlier call released. Act only on
   `task_read`, and never call `team_sync` from a nested tool call.
3. Interrupt fallback can leave an Alert queued. When a provider ignores the
   abort for the full 10-second wait, the Alert is admitted while the run is
   busy. When that run then ends by abort, the Alert waits until the next input
   starts a run. An ordinary Alert queued before a run-only abort behaves the
   same. The cause is pi-durable 1.4.0: an aborted run does not drain its inbox.
4. An Alert can be admitted after its recipient is closed or fenced. After an
   owner Close, a busy Worker can still run one tool call.
